# Ключевые решения

Здесь записано, **почему** проект устроен именно так. Формат каждой записи:
что выбрали, какие были варианты и что это значит на практике.
Новые решения дописываются в конец по мере работы.

---

## 1. Интерфейс: HTMX + шаблоны Jinja2, а не React

**Что выбрали.** HTML-страницы собирает сервер из шаблонов. Там, где нужно обновить
кусочек страницы без перезагрузки, используется HTMX — один небольшой JS-файл.

**Почему.** React — это отдельный мир: язык JavaScript, сборщик, пакеты npm, второе
приложение рядом с первым. Для новичка это двойная нагрузка. С HTMX весь проект
написан на Python и HTML, и его можно читать, зная только их.

**Как это выглядит.** В `app/templates/home.html` есть блок с атрибутом
`hx-get="/partials/status"`. HTMX видит его, запрашивает этот адрес и вставляет
ответ сервера внутрь блока. Ни строчки JavaScript писать не пришлось.

## 2. База данных: SQLite

**Что выбрали.** Вся база — один файл `data/app.db`.

**Почему.** Пользователь один, данных мало. SQLite не требует отдельного сервера,
а перенос и резервная копия — это копирование одного файла. PostgreSQL понадобится
в проектах, где много пользователей одновременно; до него дойдём на этапе 2 обучения.

## 3. SQLAlchemy в обычном (синхронном) режиме

**Что выбрали.** Функции маршрутов объявлены через `def`, а не `async def`.

**Почему.** Асинхронный код быстрее при тысячах одновременных запросов, но заметно
сложнее для чтения. У нас один пользователь — выигрыша нет, а простота важна.

## 4. Миграции Alembic, которые применяются при старте

**Что выбрали.** Структура базы меняется только через миграции — небольшие файлы
в папке `migrations/versions/`, каждый описывает один шаг («создать таблицу»).
Контейнер при запуске сам выполняет `alembic upgrade head`.

**Почему.** Когда в приложении появится новая таблица, твоя база с прогрессом
обновится сама и без потери данных. Без миграций базу пришлось бы удалять и создавать заново.

**Деталь.** Папка называется `migrations/`, а не `alembic/` (как по умолчанию): так
понятнее назначение, и имя папки не совпадает с именем библиотеки.

## 5. Три слоя: маршруты → сервисы → модели

**Что выбрали.**

- `app/routers/` — принимает запрос, отдаёт ответ. Логики здесь нет.
- `app/services/` — логика («проверить базу», позже «составить план недели»).
- `app/models/` — описание таблиц.

**Почему.** Логику в сервисах можно проверять тестами без браузера и веб-сервера.
А когда что-то сломается, сразу ясно, в какой папке искать.

## 6. Зависимости в requirements.txt

**Что выбрали.** Библиотеки перечислены в `requirements.txt` (для работы) и
`requirements-dev.txt` (для тестов и линтера), версии зафиксированы через `==`.

**Почему.** Это самый простой и распространённый формат: одна строка — одна
библиотека. Фиксация версий гарантирует, что через полгода проект соберётся так же, как сегодня.

## 7. Один Docker-образ вместе с инструментами разработки

**Что выбрали.** В образ установлены и pytest, и ruff, поэтому `make test` и
`make lint` работают внутри контейнера.

**Почему.** Тебе не нужно ставить Python на Windows — достаточно Docker.
Для сервера в интернете так не делают (лишнее в образе), но это локальное приложение.
Разделим образы, когда дойдём до темы деплоя.

## 8. Без логина, порт открыт только для своего компьютера

**Что выбрали.** В `docker-compose.yml` порт записан как `127.0.0.1:8000:8000`.

**Почему.** `127.0.0.1` — адрес «самого себя». Сайт открывается только с того
компьютера, где запущен, поэтому пароль не нужен. Если убрать `127.0.0.1:`, сайт
станет виден всей домашней сети — тогда уже стоит подумать о защите.

## 9. Никаких внешних ресурсов (CDN)

**Что выбрали.** Файл `htmx.min.js` лежит в `app/static/js/`, шрифты — системные,
стили — свой файл `style.css`.

**Почему.** Требование проекта: после сборки всё работает без интернета. За этим
следит тест `test_pages_do_not_load_anything_from_the_internet`.

## 10. Тесты работают с временной базой

**Что выбрали.** Для каждого теста создаётся отдельная пустая база во временной папке
(см. `tests/conftest.py`).

**Почему.** Тесты не должны портить настоящий прогресс и не должны зависеть друг от друга.
Отдельный тест проверяет, что модели в коде совпадают с миграциями — он упадёт,
если изменить модель и забыть создать миграцию.

## 11. Окончания строк: всегда LF

**Что выбрали.** Файл `.gitattributes` заставляет git хранить текст с окончаниями
строк в стиле Linux (LF).

**Почему.** Windows ставит в конце строки два символа (CRLF), Linux — один (LF).
Код запускается в Linux-контейнере, и «виндовые» окончания могут ломать скрипты.

## 12. Работа идёт в ветке develop

**Что выбрали.** Новые этапы коммитятся в ветку `develop`. Ветка `main` — для
проверенных версий.

**Почему.** Так принято в командах: в `main` попадает только то, что проверено.
Заодно это практика работы с ветками git.
