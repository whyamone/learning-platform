# Ключевые решения

Здесь записано, **почему** проект устроен именно так. Формат каждой записи:
что выбрали, какие были варианты и что это значит на практике.
Новые решения дописываются в конец по мере работы.

---

## 1. Интерфейс: HTMX + шаблоны Jinja2, а не React

**Что выбрали.** HTML-страницы собирает сервер из шаблонов. Там, где нужно обновить
кусочек страницы без перезагрузки, используется HTMX — один небольшой JS-файл.

**Почему.** React — это отдельный мир: язык JavaScript, сборщик, пакеты npm, второе
приложение рядом с первым. Для новичка это двойная нагрузка. С HTMX весь проект
написан на Python и HTML, и его можно читать, зная только их.

**Как это выглядит.** В `app/templates/home.html` есть блок с атрибутом
`hx-get="/partials/status"`. HTMX видит его, запрашивает этот адрес и вставляет
ответ сервера внутрь блока. Ни строчки JavaScript писать не пришлось.

## 2. База данных: SQLite

**Что выбрали.** Вся база — один файл `data/app.db`.

**Почему.** Пользователь один, данных мало. SQLite не требует отдельного сервера,
а перенос и резервная копия — это копирование одного файла. PostgreSQL понадобится
в проектах, где много пользователей одновременно; до него дойдём на этапе 2 обучения.

## 3. SQLAlchemy в обычном (синхронном) режиме

**Что выбрали.** Функции маршрутов объявлены через `def`, а не `async def`.

**Почему.** Асинхронный код быстрее при тысячах одновременных запросов, но заметно
сложнее для чтения. У нас один пользователь — выигрыша нет, а простота важна.

## 4. Миграции Alembic, которые применяются при старте

**Что выбрали.** Структура базы меняется только через миграции — небольшие файлы
в папке `migrations/versions/`, каждый описывает один шаг («создать таблицу»).
Контейнер при запуске сам выполняет `alembic upgrade head`.

**Почему.** Когда в приложении появится новая таблица, твоя база с прогрессом
обновится сама и без потери данных. Без миграций базу пришлось бы удалять и создавать заново.

**Деталь.** Папка называется `migrations/`, а не `alembic/` (как по умолчанию): так
понятнее назначение, и имя папки не совпадает с именем библиотеки.

## 5. Три слоя: маршруты → сервисы → модели

**Что выбрали.**

- `app/routers/` — принимает запрос, отдаёт ответ. Логики здесь нет.
- `app/services/` — логика («проверить базу», позже «составить план недели»).
- `app/models/` — описание таблиц.

**Почему.** Логику в сервисах можно проверять тестами без браузера и веб-сервера.
А когда что-то сломается, сразу ясно, в какой папке искать.

## 6. Зависимости в requirements.txt

**Что выбрали.** Библиотеки перечислены в `requirements.txt` (для работы) и
`requirements-dev.txt` (для тестов и линтера), версии зафиксированы через `==`.

**Почему.** Это самый простой и распространённый формат: одна строка — одна
библиотека. Фиксация версий гарантирует, что через полгода проект соберётся так же, как сегодня.

## 7. Один Docker-образ вместе с инструментами разработки

**Что выбрали.** В образ установлены и pytest, и ruff, поэтому `make test` и
`make lint` работают внутри контейнера.

**Почему.** Тебе не нужно ставить Python на Windows — достаточно Docker.
Для сервера в интернете так не делают (лишнее в образе), но это локальное приложение.
Разделим образы, когда дойдём до темы деплоя.

## 8. Без логина, порт открыт только для своего компьютера

**Что выбрали.** В `docker-compose.yml` порт записан как `127.0.0.1:8000:8000`.

**Почему.** `127.0.0.1` — адрес «самого себя». Сайт открывается только с того
компьютера, где запущен, поэтому пароль не нужен. Если убрать `127.0.0.1:`, сайт
станет виден всей домашней сети — тогда уже стоит подумать о защите.

## 9. Никаких внешних ресурсов (CDN)

**Что выбрали.** Файл `htmx.min.js` лежит в `app/static/js/`, шрифты — системные,
стили — свой файл `style.css`.

**Почему.** Требование проекта: после сборки всё работает без интернета. За этим
следит тест `test_pages_do_not_load_anything_from_the_internet`.

## 10. Тесты работают с временной базой

**Что выбрали.** Для каждого теста создаётся отдельная пустая база во временной папке
(см. `tests/conftest.py`).

**Почему.** Тесты не должны портить настоящий прогресс и не должны зависеть друг от друга.
Отдельный тест проверяет, что модели в коде совпадают с миграциями — он упадёт,
если изменить модель и забыть создать миграцию.

## 11. Окончания строк: всегда LF

**Что выбрали.** Файл `.gitattributes` заставляет git хранить текст с окончаниями
строк в стиле Linux (LF).

**Почему.** Windows ставит в конце строки два символа (CRLF), Linux — один (LF).
Код запускается в Linux-контейнере, и «виндовые» окончания могут ломать скрипты.

## 12. Ветки develop и main

**Что выбрали.** Работа над этапом идёт в ветке `develop`. Когда этап готов
и проверен, он попадает в `main`.

**Почему.** `main` — то, что скачивается по умолчанию, поэтому там всегда рабочая
версия. Заодно это практика работы с ветками git.

## 13. Учебные материалы — файлы, а не записи в базе

**Что выбрали.** Темы лежат в папке `content/` как Markdown-файлы с «шапкой» YAML.
При запуске приложение читает их и переносит в базу.

**Почему.** Файл можно открыть в любом редакторе, поправить без программирования
и сохранить в git вместе с историей правок. База при этом остаётся удобной для
поиска и подсчёта прогресса.

**Как устроено.** Импорт разделён на два файла:

- `content_loader.py` только читает файлы и проверяет их. О базе он не знает.
- `importer.py` берёт прочитанное и записывает в базу.

Такое разделение позволяет проверить чтение файлов тестами без базы данных.

## 14. Импорт обновляет записи, а не пересоздаёт их

**Что выбрали.** При импорте тема ищется по короткому имени (slug) из имени файла.
Нашлась — обновляем текст. Не нашлась — создаём. Файл исчез — тема помечается
скрытой (`is_active = false`), но не удаляется.

**Почему.** К теме привязан твой прогресс, а позже — заметки и карточки.
Если бы импорт удалял и создавал темы заново, всё это терялось бы при каждой правке.
Обратная сторона: если переименовать файл, получится новая тема без прогресса.

## 15. Ошибка в файле не роняет приложение

**Что выбрали.** Файл с ошибкой пропускается, а сообщение («в таком-то файле
не заполнено поле title») показывается вверху дорожной карты.

**Почему.** Опечатка в одном файле не должна мешать пользоваться остальными
темами. А понятное сообщение на странице избавляет от чтения логов.

## 16. Прогресс хранится отдельно от содержимого

**Что выбрали.** Статус темы лежит в таблице `topic_progress`, а не в таблице `topics`.

**Почему.** В `topics` — то, что приходит из файлов и может быть перезаписано.
В `topic_progress` — то, что создаёшь ты. Две таблицы не дают случайно затереть
одно другим.

## 17. «Повторить» считается пройденной темой

**Что выбрали.** В проценте прогресса учитываются статусы «Готово» и «Повторить».

**Почему.** «Повторить» означает: тема изучена, но к ней стоит вернуться.
Если бы такая пометка уменьшала процент, отмечать темы честно было бы невыгодно.

## 18. Markdown превращается в HTML при показе страницы

**Что выбрали.** В базе хранится исходный Markdown. В HTML он переводится каждый
раз, когда открывается страница темы. Код подсвечивает библиотека Pygments на сервере.

**Почему.** Так проще: нет второй копии текста, которая может устареть. Для одного
пользователя это занимает миллисекунды. Подсветка на сервере не требует JavaScript
и работает без интернета.

**Про безопасность.** HTML-теги внутри Markdown не выполняются, а показываются
как текст. Сейчас материалы пишешь ты сам, но на этапе с ИИ-наставником текст
будет приходить от модели — и эта защита станет важной.

## 19. Кнопки статуса работают и без JavaScript

**Что выбрали.** Кнопки статуса — обычная HTML-форма. HTMX лишь улучшает её:
обновляет один блок вместо перезагрузки всей страницы.

**Почему.** Это называется «прогрессивное улучшение»: основа работает везде,
удобства добавляются сверху. Сервер отличает запрос HTMX по заголовку `HX-Request`
и отвечает либо кусочком HTML, либо перенаправлением на страницу темы.

## 20. У каждой темы есть оценка в часах

**Что выбрали.** В шапке темы указано поле `estimated_hours` — сколько времени
она примерно займёт вместе с практикой.

**Почему.** Без этого числа нельзя ни разложить темы по неделям, ни спрогнозировать
дату окончания этапа. Сумма по всем темам — около 690 часов при доступных 1000:
запас оставлен намеренно, на повторение и пропуски. Оценки приблизительные —
поправь их в файлах, когда увидишь свой настоящий темп.

## 21. Заготовки помечены явно

**Что выбрали.** У тем без подробной теории в шапке стоит `stub: true`,
и на карте рядом с ними написано «заготовка».

**Почему.** Честнее показать, что тема ещё не раскрыта, чем делать вид, будто
три абзаца — это полный урок. Заготовка всё равно полезна: в ней есть цель,
понятия, задание и ссылки, по которым можно учиться.

## 22. Ссылки проверяются программой, а не на глаз

**Что выбрали.** Команда `make check-links` обходит все ссылки из материалов
и печатает те, что не открываются, вместе с файлом, где они записаны.

**Почему.** В материалах около 130 разных адресов, и сайты со временем переезжают.
Проверять вручную долго, а битая ссылка в начале занятия сбивает настрой.
Программа лежит в `app/tools/` — это пример кода, который запускается
из терминала, а не через сайт.

## 23. Линтер не трогает учебные материалы

**Что выбрали.** Папка `content/` исключена из проверки `ruff`.

**Почему.** `ruff` умеет форматировать примеры кода внутри Markdown. Но в уроках
код иногда нарочно написан «неправильно» — чтобы показать ошибку или два способа
записи. Автоматическое исправление испортило бы такие примеры.

## 24. Квизы и карточки — тоже файлы рядом с темой

**Что выбрали.** Вопросы лежат в `<тема>.quiz.yaml`, карточки — в `<тема>.cards.yaml`,
в той же папке, что и файл темы.

**Почему.** Всё, что относится к теме, лежит рядом и правится в любом редакторе.
Отдельные файлы, а не одна большая «шапка», потому что список вопросов длинный
и читать его внутри темы было бы неудобно.

## 25. SM-2 — отдельная «чистая» функция

**Что выбрали.** Алгоритм повторений записан в `app/services/sm2.py` как функция
`next_schedule(расписание, оценка) → новое расписание`. Она не знает ни о базе, ни о сайте.

**Почему.** Чистую функцию легко проверить: подал числа — сравнил результат.
Тесты в `tests/test_sm2.py` выполняются за миллисекунды и не требуют базы.
А связь с базой — отдельный файл `cards.py`. Если захочется заменить SM-2
на другой алгоритм, меняться будет один файл.

## 26. Четыре кнопки вместо шести оценок

**Что выбрали.** В SM-2 ответ оценивается числом от 0 до 5. В интерфейсе четыре
кнопки: «Не помню» (1), «С трудом» (3), «Хорошо» (4), «Легко» (5).

**Почему.** Выбирать из шести вариантов после каждой карточки утомительно,
а разница между 0, 1 и 2 для расчёта мала — все они означают «не вспомнил».
Так же поступает Anki. Под каждой кнопкой показано, когда карточка вернётся, —
чтобы оценка была осознанной.

**Упрощение.** Забытая карточка возвращается завтра, а не в тот же день,
как в полном SM-2. Так очередь всегда заканчивается, и занятие не затягивается.

## 27. Карточки открываются вместе с темой и выдаются понемногу

**Что выбрали.** Карточки появляются в очереди, только когда тема переведена
из «Не начато». Новых карточек — не больше десяти в день (настройка `NEW_CARDS_PER_DAY`).

**Почему.** Повторять то, чего ещё не изучал, бессмысленно. А без дневного
лимита после большой темы навалилось бы тридцать новых карточек разом —
верный способ бросить повторение.

## 28. Расписание карточки привязано к тексту вопроса

**Что выбрали.** Импорт узнаёт карточку по «отпечатку» — хешу названия темы
и текста вопроса. Расписание хранится в отдельной таблице `card_states`.

**Почему.** У карточки в файле нет номера, а порядок может меняться.
Отпечаток позволяет править ответ и переставлять карточки, не теряя расписания.
Обратная сторона: изменённый вопрос считается новой карточкой.
Вопросы квиза, наоборот, при импорте просто заменяются — к ним ничего не привязано,
в истории попыток хранится только счёт.

## 29. Один маршрут с async — исключение из решения 3

**Что выбрали.** Маршрут приёма ответов квиза объявлен через `async def`.

**Почему.** У каждой темы своё число вопросов, поэтому поля формы заранее
неизвестны, и форму приходится читать целиком: `await request.form()`.
А `await` разрешён только внутри async-функции. Остальные маршруты остаются обычными.

## 30. «Сегодня» определяется по часовому поясу из настроек

**Что выбрали.** Дата для очереди карточек берётся из настройки `TIMEZONE`,
а не из часов контейнера. Время событий в базе по-прежнему хранится в UTC.

**Почему.** Внутри контейнера часы идут по UTC. Без поправки новый день
в приложении начинался бы в три часа ночи по Москве, а в Красноярске — в семь утра.
Сведения о поясах берутся из пакета `tzdata`: в облегчённом образе Python их нет.

## 31. Таймер живёт в базе, а не в браузере

**Что выбрали.** При нажатии «Начать занятие» в базу записывается время начала.
Сколько минут прошло, сервер вычисляет при каждом показе страницы. Строку
с таймером в шапке HTMX перезапрашивает раз в минуту.

**Почему.** Таймер на JavaScript остановился бы при закрытии вкладки
или перезагрузке компьютера. Запись в базе этого не боится: можно закрыть
браузер, вернуться через час и нажать «Закончить». Заодно не понадобилось
ни строчки своего JavaScript.

## 32. Забытый таймер не портит статистику

**Что выбрали.** Таймер засчитывает не больше пяти часов. Занятие короче минуты
не записывается. Любую запись можно исправить или удалить на странице «Время».

**Почему.** Таймер, забытый на ночь, дал бы четырнадцать «часов учёбы»
и испортил бы темп и прогноз. Ограничение сверху и возможность правки
делают статистику честной без лишних вопросов к тебе.

## 33. У занятия хранится местная дата

**Что выбрали.** В таблице занятий есть столбец `day` — дата по твоему часовому поясу.
Точное время начала и конца хранится отдельно в UTC.

**Почему.** Неделя, серия дней и темп считаются по дням. Если каждый раз
переводить время из UTC в местное, запросы усложняются, а занятие в час ночи
легко уезжает на соседний день. Готовая дата делает запросы простыми:
«сумма минут, сгруппированная по дню».

## 34. Серия дней не наказывает

**Что выбрали.** Серия считается по вчерашний день включительно, пока сегодня
ты ещё не занимался. В серию идут и занятия, и повторение карточек.
Рядом показывается лучшая серия за всё время.

**Почему.** Если бы счётчик обнулялся в полночь, утром ты видел бы ноль —
хотя серия ещё не прервана. А пять минут на карточки в загруженный день —
тоже учёба, и они сохраняют серию. Лучшая серия остаётся с тобой,
даже если текущая оборвалась.

## 35. Прогноз — это деление, а не обещание

**Что выбрали.** Дата завершения этапа = оставшиеся часы ÷ темп. Темп —
среднее за четыре недели. В первые две недели занятий берётся плановый темп,
и на дашборде это прямо написано: одно занятие в первый день не должно
превращаться в «темп 2 часа в неделю» и прогноз на годы вперёд.

**Почему.** Простую формулу легко понять и проверить в уме. Сложная модель
выглядела бы точнее, но на таких данных точнее не была бы. Прогноз
пересчитывается при каждом открытии страницы, поэтому пропуск не нужно
«отрабатывать» — дата сдвигается сама.

## 36. График недели сделан без JavaScript

**Что выбрали.** Столбцы — обычные блоки, высота которых задана в процентах
прямо в HTML. Значение показано над столбцом и во всплывающей подсказке.

**Почему.** Для семи столбцов библиотека графиков не нужна. Это меньше кода,
работает без интернета и читается как обычный шаблон. Один ряд данных —
один цвет: цвет здесь ничего не кодирует, поэтому и легенда не нужна.

## 37. Ссылки в журнале проверяются

**Что выбрали.** В поле ссылки принимаются только адреса, начинающиеся
с `http://` или `https://`.

**Почему.** В атрибут `href` можно подставить адрес вида `javascript:…`,
который при нажатии выполнит код. Даже в приложении для одного пользователя
полезно привыкать: всё, что пришло из формы, проверяется перед сохранением.

## 38. План не хранится, а вычисляется

**Что выбрали.** Таблицы с планом нет. Функция `build_plan` строит его заново
при каждом открытии страницы из расписания, непройденных тем, записанных занятий
и сегодняшней даты.

**Почему.** Требование звучало так: пропустил занятие — план пересчитывается
без чувства вины. Если бы план лежал в базе, пришлось бы придумывать пометки
«пропущено», переносить задачи и следить, чтобы план не расходился с реальностью.
Вычисляемый план не может устареть: «долгов» в нём не бывает по построению.
Проверяет это тест `test_missed_day_just_shifts_topics`.

**Обратная сторона.** Нельзя вручную перетащить тему на другой день.
Для одного пользователя это честный обмен: меньше возни, больше учёбы.

## 39. Планировщик — чистая функция

**Что выбрали.** `build_plan` не обращается к базе. Данные для неё собирают
отдельные функции (`collect_plan_topics`, `get_studied_by_day`).

**Почему.** Так же, как с SM-2 в решении 25: логику раскладки можно проверить
на придуманных данных за миллисекунды. В тестах темы — простые заготовки
с названием, база для них не нужна.

## 40. Расписание хранится в базе, а не в .env

**Что выбрали.** Расписание лежит в таблице `settings` одной строкой JSON
и меняется формой на странице «План». Настройка `WEEKLY_GOAL_HOURS` из `.env`
убрана: план на неделю теперь равен сумме часов в расписании.

**Почему.** Расписание меняется вместе с жизнью — сессия, отпуск, новая смена.
Править для этого файл и перезапускать контейнер неудобно. А два числа
(«часов в неделю» и «расписание») неизбежно разошлись бы — поэтому осталось одно.
Правило проекта: в `.env` — то, что относится к установке (часовой пояс,
адреса), в базе — то, что меняет пользователь в интерфейсе.

## 41. Остаток времени на тему считается по таймеру

**Что выбрали.** Планировщик отводит теме «оценка минус уже записанное время».
Если потрачено больше оценки, а тема не закрыта, ей оставляется полчаса.

**Почему.** Так план учитывает сделанное без ручных отметок. А оценки часов
приблизительны: тема, которая идёт дольше, не должна пропадать из плана.

## 42. Карточки и «освежить» идут первыми

**Что выбрали.** В каждом учебном дне сначала 10 минут карточек, затем темы
с пометкой «Повторить», и только потом новый материал.

**Почему.** Повторение даёт больше всего пользы на минуту времени, но его
легче всего отложить. Если оно стоит первым пунктом, до него доходит очередь.

## 43. Наставник включается флагом и ничего не ломает, когда выключен

**Что выбрали.** Настройка `AI_MENTOR_ENABLED` по умолчанию `false`. Когда она
выключена, блок чата не рисуется, а маршруты наставника отвечают «404».

**Почему.** Наставнику нужны Ollama и видеокарта, а остальному приложению — нет.
Необязательная часть не должна мешать обязательной. Проверка вынесена
в одну функцию-зависимость `require_mentor`: все маршруты наставника получают
её через `Depends`, поэтому забыть проверку в одном из них нельзя.

## 44. С моделью говорим по OpenAI-совместимому API

**Что выбрали.** Запрос к модели — обычный POST на `/chat/completions`
со списком сообщений. Специальная библиотека Ollama не используется.

**Почему.** Этот формат понимают Ollama, vLLM и многие облачные сервисы.
Чтобы сменить поставщика модели, достаточно поменять адрес и имя модели в `.env`.
А ещё так лучше видно, что происходит на самом деле: один HTTP-запрос, один JSON-ответ.

## 45. Модель получает материалы темы в системной инструкции

**Что выбрали.** Перед каждым запросом собирается инструкция: роль наставника,
правила выбранного режима и материалы темы — цель, понятия, теория, практика.
Затем идут последние реплики разговора и новый вопрос.

**Почему.** Модель ничего не помнит между запросами и не знает, какая тема
открыта. Всё, что ей нужно, приходится передавать каждый раз. Это простейший
вариант подхода, который на третьем этапе обучения называется RAG.

**Ограничение.** У локальных моделей маленькое контекстное окно, поэтому
теория обрезается до 3500 символов, а из истории берутся восемь последних реплик.

## 46. Ответ приходит целиком, а не по буквам

**Что выбрали.** Запрос отправляется без потоковой выдачи. Пока модель думает,
показывается надпись, а кнопка отправки отключена.

**Почему.** Потоковая выдача приятнее, но требует дополнительного JavaScript
и заметно усложняет код. Для первой версии важнее, чтобы код читался.
Это хорошее улучшение на будущее — после темы «Стриминг» на третьем этапе.

## 47. Сбой модели — не ошибка приложения

**Что выбрали.** Любая неудача (Ollama не запущена, модель не скачана,
истекло время, пришёл непонятный ответ) превращается в понятное сообщение
в блоке чата. Набранный текст возвращается в поле ввода. В историю попадают
только пары «вопрос — ответ».

**Почему.** Внешний сервис может быть недоступен в любой момент — это норма,
а не исключительная ситуация. Страница при этом должна остаться рабочей,
а пользователь — понять, что делать.

## 48. Ответ модели считается недоверенным текстом

**Что выбрали.** Ответ показывается через тот же преобразователь Markdown,
что и теория: HTML-теги в нём не выполняются. Блоки `<think>…</think>`,
в которых некоторые модели «размышляют вслух», вырезаются.

**Почему.** Модель может вернуть что угодно, в том числе тег `<script>`.
Это то самое правило из решения 18, ради которого оно и было принято.
