# Теория

## Что изменилось: git diff

```bash
git diff                    # изменения в рабочей папке, ещё не в индексе
git diff --staged           # изменения в индексе, которые войдут в коммит
git diff a1b2c3d e4f5a6b    # разница между двумя коммитами
git show a1b2c3d            # что изменил конкретный коммит
```

В выводе строки с `-` — удалённые, с `+` — добавленные. Привычка смотреть
`git diff --staged` перед каждым коммитом спасает от случайных правок.

## История

```bash
git log --oneline --graph         # компактно, с ветвлениями
git log -p hello.py               # история изменений одного файла
git log --since="1 week ago"
git blame hello.py                # кто и когда менял каждую строку
```

## Отмена на каждом шаге

Какую команду выбрать, зависит от того, где находится изменение.

| Ситуация | Команда |
|---|---|
| Испортил файл, хочу вернуть как в последнем коммите | `git restore файл` |
| Добавил в индекс лишнее | `git restore --staged файл` |
| Ошибся в сообщении последнего коммита | `git commit --amend -m "новое"` |
| Забыл файл в последнем коммите | `git add файл`, затем `git commit --amend --no-edit` |
| Коммит оказался ошибочным | `git revert идентификатор` |

> `git restore файл` безвозвратно уничтожает несохранённые изменения
> в этом файле. Git не сможет их вернуть: в историю они не попадали.

## revert и reset

Оба отменяют коммиты, но по-разному.

**`git revert`** создаёт **новый** коммит, который делает обратное.
История остаётся целой — это безопасно всегда.

```bash
git revert a1b2c3d
```

**`git reset`** передвигает указатель ветки назад, как будто коммитов не было.

```bash
git reset --soft HEAD~1     # убрать коммит, изменения оставить в индексе
git reset --mixed HEAD~1    # убрать коммит, изменения оставить в рабочей папке
git reset --hard HEAD~1     # убрать коммит И уничтожить изменения
```

`HEAD~1` означает «на один коммит назад от текущего».

Правило: коммиты, которые уже отправлены на GitHub, отменяй через `revert`.
`reset` применяй только к тому, что есть лишь у тебя. А `--hard` — только
когда точно знаешь, что теряешь.

Если что-то всё же пропало, загляни в `git reflog`: там записаны все
перемещения указателя, и коммит часто удаётся вернуть.

## Файл .gitignore

Не всё должно попадать в репозиторий: виртуальные окружения, служебные
папки редакторов, файлы с секретами, базы данных.

Создай в корне репозитория файл `.gitignore`:

```text
# Виртуальное окружение и служебные файлы Python
.venv/
__pycache__/
*.pyc

# Секреты
.env

# Редакторы и операционные системы
.vscode/
.DS_Store

# Логи и временные файлы
*.log
```

Каждая строка — шаблон. Файлы, подходящие под него, Git перестаёт замечать.

Если файл уже попал в репозиторий, одного `.gitignore` мало:

```bash
git rm --cached secrets.env     # убрать из репозитория, оставить на диске
```

> Пароль, попавший в коммит, остаётся в истории даже после удаления файла.
> Если это случилось, пароль считается раскрытым — его нужно сменить.

# Практика

**Задание 1.** Измени файл, посмотри `git diff`. Добавь в индекс
и посмотри `git diff` и `git diff --staged`. Объясни разницу.

**Задание 2.** Испорти любой файл (удали половину содержимого) и верни его
в исходное состояние одной командой.

**Задание 3.** Сделай коммит с опечаткой в сообщении и исправь сообщение.

**Задание 4.** Сделай коммит, который ломает программу. Отмени его через
`git revert` и посмотри, как это выглядит в истории.

**Задание 5.** Сделай два пробных коммита и убери их через `git reset --soft`.
Посмотри `git status`. Повтори с `--hard` и сравни.

**Задание 6.** Создай `.gitignore` для своего репозитория. Проверь:
создай папку `.venv` и файл `test.log` — в `git status` их быть не должно.

**Задание 7 (со звёздочкой).** После `git reset --hard` найди «потерянный»
коммит через `git reflog` и верни его.
