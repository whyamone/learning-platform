# Теория

## Что такое pull request

Pull request (PR) — предложение влить одну ветку в другую. В команде
никто не отправляет изменения прямо в `main`: сначала создаётся PR,
коллеги смотрят код, автоматика запускает тесты, и только потом
ветка сливается.

Работая в одиночку, тоже полезно привыкать к этому порядку: именно так
устроена работа в любой компании.

## Полный цикл

```bash
git switch -c add-json-export       # 1. ветка под задачу
# ...работа, коммиты...
git push -u origin add-json-export  # 2. отправить ветку на GitHub
```

3. На странице репозитория появится кнопка **Compare & pull request**.
4. Заполни заголовок и описание: что сделано и зачем.
5. Открой вкладку **Files changed** и просмотри собственные изменения.
6. Нажми **Merge pull request**, затем **Delete branch**.
7. Обнови локальную копию:

```bash
git switch main
git pull
git branch -d add-json-export
```

## Хорошее описание PR

- **Что сделано** — одной-двумя фразами.
- **Зачем** — какую задачу это решает.
- **Как проверить** — команды или шаги.

Небольшой PR на одну задачу проверяют быстро и внимательно.
PR на тысячу строк не читает никто.

## Проверка кода

Просмотр своего кода во вкладке **Files changed** перед слиянием —
привычка, которая ловит забытые отладочные `print()`, случайные файлы
и опечатки. На работе твой код будут проверять коллеги, а ты — их.

## README — лицо проекта

Файл `README.md` в корне репозитория показывается на его главной странице.
Работодатель, открывший твой проект, прочтёт его первым — и часто единственным.

Что должно быть в README:

1. **Название и одна фраза** — что это за программа.
2. **Возможности** — коротким списком.
3. **Установка и запуск** — команды, которые можно скопировать.
4. **Пример использования** — команда и её вывод.
5. **Как устроено** — если проект не совсем простой.

## Markdown

README пишется в формате Markdown — в нём же написаны темы этой платформы.

```markdown
# Заголовок первого уровня
## Заголовок второго уровня

Обычный текст, **жирный**, *курсив*, `код в строке`.

- пункт списка
- ещё пункт

1. нумерованный
2. список

[текст ссылки](https://example.com)
```

Блок кода оформляется тройными обратными кавычками с названием языка —
тогда GitHub подсветит синтаксис.

## Профиль как портфолио

- Закрепи на странице профиля лучшие репозитории (**Customize your pins**).
- Дай репозиториям понятные имена и короткие описания.
- Регулярные коммиты показывают, что ты действительно пишешь код.
- Лучше три законченных проекта с хорошим README, чем двадцать заброшенных.

## Issues

**Issue** — запись о задаче или ошибке. Удобно вести в них список дел
по проекту. Если в описании PR написать `Closes #3`, то при слиянии
задача номер 3 закроется сама.

# Практика

**Задание 1.** Напиши `README.md` для своего репозитория `study`:
что в нём лежит, как запустить примеры, чему ты уже научился.

**Задание 2.** Создай ветку, добавь в ней новую программу, отправь ветку
на GitHub и открой pull request с описанием по трём пунктам из теории.

**Задание 3.** Просмотри свои изменения во вкладке **Files changed**.
Оставь комментарий к одной из строк. Слей PR и удали ветку.

**Задание 4.** Создай три issue с задачами по улучшению своих программ.
Одну реши через PR, указав в описании `Closes #номер`.

**Задание 5.** Оформи профиль: фото или аватар, короткое описание,
закреплённые репозитории.

**Задание 6 (со звёздочкой).** Найди на GitHub открытый проект с меткой
`good first issue` и прочитай его инструкцию для участников
(файл `CONTRIBUTING.md`). Вносить изменения пока не обязательно —
достаточно понять, как устроен процесс.
