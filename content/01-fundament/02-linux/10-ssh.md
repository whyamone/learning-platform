# Теория

## Что такое SSH

SSH — протокол для безопасной работы на удалённом компьютере. Ты набираешь
команды у себя, а выполняются они на сервере. Весь обмен зашифрован.

Как сетевой инженер ты подключаешься так к оборудованию. Для разработчика SSH —
способ попасть на сервер, где работает его программа, и способ связи с GitHub.

Участвуют две программы: **клиент** `ssh` на твоём компьютере
и **сервер** `sshd` на удалённом. Стандартный порт — 22.

## Подключение

```bash
ssh ivan@192.168.1.10             # пользователь@адрес
ssh -p 2222 ivan@192.168.1.10     # нестандартный порт
ssh ivan@192.168.1.10 "uptime"    # выполнить одну команду и выйти
```

Выход из сеанса — команда `exit` или `Ctrl+D`.

## Где потренироваться

Удалённого сервера у тебя пока нет, но SSH-сервер можно поднять в самой Ubuntu
и подключаться к ней же.

```bash
sudo apt install -y openssh-server
sudo systemctl start ssh
ssh $USER@localhost
```

Все приёмы этой темы работают и при подключении к `localhost`.

## Первое подключение и known_hosts

При первом подключении к узлу появится вопрос:

```text
The authenticity of host '192.168.1.10' can't be established.
ED25519 key fingerprint is SHA256:Xk3...
Are you sure you want to continue connecting (yes/no)?
```

Клиент показывает **отпечаток** ключа сервера и спрашивает, доверяешь ли ты ему.
После ответа `yes` отпечаток сохраняется в файле `~/.ssh/known_hosts`.

При следующих подключениях клиент сверяет отпечаток. Если он изменился,
появится грозное предупреждение `REMOTE HOST IDENTIFICATION HAS CHANGED`.
Причин две: сервер переустановили — или кто-то пытается выдать себя за него.
Не игнорируй это сообщение, пока не выяснишь причину.

Если причина известна и безопасна, старую запись удаляют:

```bash
ssh-keygen -R 192.168.1.10
```

## Ключи вместо паролей

Пароль можно подобрать или подсмотреть. Надёжнее входить по **паре ключей**.

- **Закрытый ключ** хранится только у тебя и никогда никуда не передаётся.
- **Открытый ключ** кладётся на сервер. Его можно показывать кому угодно.

Удобное сравнение: открытый ключ — это замок, закрытый — ключ к нему.
Замки можно раздать всем серверам. Открыть их сможет только владелец ключа.

При подключении сервер проверяет, что у тебя есть закрытый ключ, подходящий
к его «замку». Сам ключ по сети не передаётся.

## Создание ключей

```bash
ssh-keygen -t ed25519 -C "ivan@laptop"
```

`-t ed25519` — современный и надёжный тип ключа. `-C` — комментарий,
по которому потом легко понять, чей это ключ.

Программа спросит, куда сохранить (нажми Enter), и предложит задать
**парольную фразу**. Она шифрует закрытый ключ на диске: если файл украдут,
без фразы им не воспользоваться.

Появятся два файла:

| Файл | Что это | Можно ли показывать |
|---|---|---|
| `~/.ssh/id_ed25519` | закрытый ключ | **нет, никогда** |
| `~/.ssh/id_ed25519.pub` | открытый ключ | да |

```bash
ls -l ~/.ssh
cat ~/.ssh/id_ed25519.pub
```

> Закрытый ключ не отправляют в мессенджерах, не кладут в git, не копируют
> на чужие компьютеры. Если он попал в чужие руки — создай новую пару
> и удали старый открытый ключ со всех серверов.

## Установка ключа на сервер

```bash
ssh-copy-id ivan@192.168.1.10
```

Команда один раз спросит пароль и допишет твой открытый ключ в файл
`~/.ssh/authorized_keys` на сервере. Дальше вход идёт без пароля.

То же самое вручную: содержимое файла `.pub` добавляется отдельной строкой
в `~/.ssh/authorized_keys` на сервере.

## Права на файлы

SSH откажется работать, если файлы с ключами доступны другим пользователям.

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/id_ed25519.pub
chmod 600 ~/.ssh/authorized_keys
```

Если вход по ключу не работает, права — первое, что стоит проверить.

## Файл ~/.ssh/config

Чтобы не набирать каждый раз адрес, пользователя и порт, их записывают в файл настроек.

```bash
nano ~/.ssh/config
```

```text
Host lab
    HostName 192.168.1.10
    User ivan
    Port 2222
    IdentityFile ~/.ssh/id_ed25519

Host github.com
    User git
    IdentityFile ~/.ssh/id_ed25519
```

Теперь достаточно написать:

```bash
ssh lab
```

## Копирование файлов

```bash
scp report.txt lab:/home/ivan/           # с себя на сервер
scp lab:/var/log/app.log ./              # с сервера к себе
scp -r project/ lab:/home/ivan/          # папку целиком
```

Двоеточие отделяет имя узла от пути. Нет двоеточия — путь локальный.

Для больших папок удобнее `rsync`: он передаёт только изменившиеся файлы
и может продолжить после обрыва.

```bash
rsync -avz project/ lab:/home/ivan/project/
```

Опции: `a` — сохранить права и даты, `v` — показывать ход, `z` — сжимать.
Добавь `--dry-run`, чтобы увидеть, что будет сделано, ничего не меняя.

## Долгие задачи: tmux

Если связь оборвётся, программа, запущенная в сеансе SSH, завершится.
`tmux` держит сеанс на сервере независимо от подключения.

```bash
tmux new -s work          # создать сеанс с именем work
# ...запускаешь долгую задачу...
# Ctrl+B, затем D — отключиться, оставив сеанс работать
tmux ls                   # список сеансов
tmux attach -t work       # вернуться в сеанс
```

Так запускают обучение моделей и другие задачи на часы.

## Проброс портов

SSH умеет «протянуть» порт удалённого сервера к себе на компьютер.

```bash
ssh -L 8000:localhost:8000 lab
```

Пока сеанс открыт, адрес `http://localhost:8000` на твоём компьютере
ведёт на порт 8000 сервера `lab`. Так открывают веб-интерфейсы, которые
на сервере слушают только `127.0.0.1` и снаружи недоступны.

## Диагностика

```bash
ssh -v lab                # подробный ход подключения
```

В выводе видно, какие ключи пробовал клиент и на каком шаге отказ.
На стороне сервера причину показывает журнал: `journalctl -u ssh -n 30`.

## Основы безопасности сервера

Настройки сервера лежат в `/etc/ssh/sshd_config`. Для сервера, доступного
из интернета, обычно делают три вещи:

- `PasswordAuthentication no` — вход только по ключам;
- `PermitRootLogin no` — запрет входа под root;
- обновляют систему и ставят защиту от перебора паролей.

После правки файла службу перезапускают: `sudo systemctl restart ssh`.
