# Теория

## Что такое процесс

Программа — это файл на диске. **Процесс** — это программа, которая сейчас
выполняется. Одну программу можно запустить несколько раз — получится
несколько процессов.

У каждого процесса есть:

- **PID** — уникальный номер;
- **владелец** — пользователь, от имени которого он запущен;
- **родитель** — процесс, который его запустил.

## ps — список процессов

```bash
ps                    # процессы текущего терминала
ps aux                # все процессы в системе, подробно
ps aux | grep python  # найти процессы по имени
```

Главные колонки вывода `ps aux`:

| Колонка | Значение |
|---|---|
| `USER` | владелец |
| `PID` | номер процесса |
| `%CPU`, `%MEM` | доля процессора и памяти |
| `STAT` | состояние: `R` выполняется, `S` ждёт, `Z` зомби |
| `COMMAND` | команда запуска |

Быстрый поиск номера по имени:

```bash
pgrep -a python       # PID и команда всех процессов python
```

## top — наблюдение в реальном времени

```bash
top
```

Аналог диспетчера задач: список обновляется каждые несколько секунд.

| Клавиша | Действие |
|---|---|
| `P` | сортировать по процессору |
| `M` | сортировать по памяти |
| `k` | завершить процесс (спросит PID) |
| `q` | выйти |

Удобнее выглядит `htop` — он ставится командой `sudo apt install htop`.

В первой строке `top` показана **средняя загрузка** (load average) — три числа
за 1, 5 и 15 минут. Число, равное количеству ядер процессора, означает
полную загрузку.

## Сигналы и kill

Процессу нельзя «приказать» напрямую — ему посылают **сигнал**.
Команда `kill`, несмотря на название, просто отправляет сигнал.

| Сигнал | Номер | Смысл |
|---|---|---|
| `SIGTERM` | 15 | вежливая просьба завершиться; процесс успеет сохранить данные |
| `SIGKILL` | 9 | немедленное уничтожение; процесс ничего не успеет |
| `SIGINT` | 2 | прерывание с клавиатуры — то же, что `Ctrl+C` |
| `SIGHUP` | 1 | перечитать настройки |

```bash
kill 12345            # отправить SIGTERM процессу с PID 12345
kill -9 12345         # отправить SIGKILL
pkill python          # SIGTERM всем процессам с именем python
```

Порядок действий: сначала обычный `kill`. Только если процесс не реагирует
несколько секунд — `kill -9`. Принудительное завершение может оставить
повреждённые файлы.

## Фоновые задачи

Обычно команда занимает терминал, пока не закончится. Знак `&` в конце
запускает её в фоне:

```bash
sleep 300 &           # запустить в фоне; терминал свободен
jobs                  # список фоновых задач этого терминала
fg %1                 # вернуть задачу №1 на передний план
```

Уже запущенную команду можно приостановить клавишами `Ctrl+Z`,
а затем продолжить в фоне командой `bg`.

| Клавиши | Действие |
|---|---|
| `Ctrl+C` | прервать процесс |
| `Ctrl+Z` | приостановить процесс |
| `Ctrl+D` | конец ввода; в пустой строке — выход из оболочки |

Фоновая задача привязана к терминалу: закроешь окно — она завершится.
Чтобы задача пережила закрытие, используют `nohup`:

```bash
nohup python3 long_task.py > task.log 2>&1 &
```

На серверах для этого чаще применяют `tmux` — программу, которая держит
сеанс терминала даже после отключения. С ней ты познакомишься в теме про SSH.

## Службы и systemd

**Служба** — программа, которая работает постоянно в фоне: веб-сервер,
SSH-сервер, база данных. Службами управляет система `systemd`,
а команда для работы с ней — `systemctl`.

```bash
systemctl status ssh          # состояние службы
sudo systemctl start ssh      # запустить
sudo systemctl stop ssh       # остановить
sudo systemctl restart ssh    # перезапустить
sudo systemctl enable ssh     # включить автозапуск при загрузке
sudo systemctl disable ssh    # выключить автозапуск
systemctl list-units --type=service --state=running   # работающие службы
```

Различай две пары: `start`/`stop` действуют сейчас, `enable`/`disable`
определяют поведение при следующей загрузке.

> В WSL systemd может быть выключен. Если `systemctl` сообщает об ошибке,
> добавь в файл `/etc/wsl.conf` строки `[boot]` и `systemd=true`,
> затем выполни в PowerShell `wsl --shutdown` и открой Ubuntu заново.

## Журнал службы

```bash
journalctl -u ssh             # все записи службы
journalctl -u ssh -n 50       # последние 50
journalctl -u ssh -f          # следить в реальном времени
journalctl -u ssh --since "1 hour ago"
```

Порядок диагностики почти всегда одинаков: `systemctl status` — узнать,
работает ли служба, затем `journalctl -u` — узнать, почему не работает.

# Практика

**Задание 1.** Выведи все свои процессы. Найди PID оболочки, в которой работаешь.

**Задание 2.** Запусти `top`, отсортируй процессы по памяти, затем
по процессору. Найди процесс, который потребляет больше всего памяти.

**Задание 3.** Запусти `sleep 1000` в фоне. Найди его PID двумя способами.
Заверши процесс командой `kill` и убедись, что его больше нет.

**Задание 4.** Запусти `sleep 500`, приостанови через `Ctrl+Z`, продолжи
в фоне, посмотри список задач, верни на передний план и прерви.

**Задание 5.** Напиши на Python программу с бесконечным циклом, которая
раз в секунду печатает число (подсказка: `time.sleep(1)`). Запусти её в фоне
с выводом в файл. Наблюдай за файлом через `tail -f`. Заверши программу
по PID.

**Задание 6.** Выведи список работающих служб. Выбери любую и посмотри
её состояние и последние двадцать строк журнала.

**Задание 7 (со звёздочкой).** Выясни, что произойдёт с программой
из задания 5, если отправить ей `SIGTERM`, а что — если `SIGKILL`.

она печатала «Завершаю работу» и выходила без трассировки.
