# Теория

Сети ты знаешь по работе. Здесь нужно выучить, как привычные действия
выглядят в Linux, и добавить то, что важно разработчику: порты, сокеты, HTTP.

## Соответствие командам сетевого оборудования

| Задача | Cisco IOS | Linux |
|---|---|---|
| Интерфейсы и адреса | `show ip interface brief` | `ip -br addr` |
| Таблица маршрутизации | `show ip route` | `ip route` |
| Таблица ARP | `show arp` | `ip neigh` |
| Проверка связи | `ping` | `ping` |
| Трассировка | `traceroute` | `traceroute` или `tracepath` |
| Открытые порты | `show control-plane host open-ports` | `ss -tulpn` |

## Адреса и интерфейсы

```bash
ip addr               # все интерфейсы подробно
ip -br addr           # кратко: имя, состояние, адреса
ip link               # состояние интерфейсов на канальном уровне
hostname -I           # только IP-адреса этого узла
```

Интерфейс `lo` — петлевой (loopback), его адрес `127.0.0.1`.
Он есть всегда и ведёт на этот же компьютер.

## Маршруты

```bash
ip route              # таблица маршрутизации
ip route get 8.8.8.8  # через какой интерфейс и шлюз пойдёт пакет
```

Строка, начинающаяся с `default via`, — шлюз по умолчанию.

## Проверка связи

```bash
ping -c 4 8.8.8.8          # четыре запроса; без -c ping не остановится сам
tracepath ya.ru            # путь до узла
```

## DNS

```bash
cat /etc/resolv.conf       # какой DNS-сервер используется
cat /etc/hosts             # локальная таблица имён, проверяется раньше DNS
dig ya.ru                  # подробный ответ DNS
dig +short ya.ru           # только адреса
nslookup ya.ru             # то же в привычном виде
```

Файл `/etc/hosts` полезен разработчику: в нём можно дать имя локальному
сервису, не трогая DNS.

## Порты и сокеты

Для разработчика это главная часть темы. Любая серверная программа
«слушает» порт — ждёт подключений. Знать, кто какой порт занял, нужно постоянно.

```bash
ss -tulpn
```

Что означают опции: `t` — TCP, `u` — UDP, `l` — только слушающие,
`p` — показать процесс, `n` — числа вместо имён.

```text
Netid  State   Local Address:Port   Process
tcp    LISTEN  127.0.0.1:8000       users:(("python3",pid=4321,fd=6))
tcp    LISTEN  0.0.0.0:22           users:(("sshd",pid=812,fd=3))
```

Найти, кто занял конкретный порт:

```bash
ss -tulpn | grep :8000
```

## 127.0.0.1 и 0.0.0.0

Колонка `Local Address` показывает, **на каком адресе** программа принимает
подключения. Это одна из самых частых причин вопроса «почему не открывается».

| Адрес | Кто может подключиться |
|---|---|
| `127.0.0.1` | только программы на этом же компьютере |
| `0.0.0.0` | кто угодно через любой интерфейс |
| конкретный адрес | только те, кто обращается на этот адрес |

Сервер, слушающий `127.0.0.1:8000`, снаружи недоступен. Сервер
на `0.0.0.0:8000` виден всей сети.

Вспомни `docker-compose.yml` этой платформы: порт указан как
`127.0.0.1:8000:8000`, поэтому сайт открывается только с твоего компьютера.

## Проверка порта на удалённом узле

`ping` проверяет только доступность узла, но не работу сервиса на порту.

```bash
nc -zv 192.168.1.10 22         # открыт ли TCP-порт 22
nc -zv ya.ru 443
```

Опция `z` — только проверить, не передавая данных; `v` — подробный вывод.

## HTTP-запросы через curl

`curl` — универсальная программа для запросов. Ею проверяют сайты и API.

```bash
curl https://example.com               # получить страницу
curl -I https://example.com            # только заголовки ответа
curl -s https://example.com | head     # без индикатора загрузки
curl -o page.html https://example.com  # сохранить в файл
curl -v https://example.com            # показать весь обмен: запрос и ответ
```

В первой строке ответа стоит **код состояния**:

| Код | Значение |
|---|---|
| `200` | всё хорошо |
| `301`, `302` | перенаправление на другой адрес |
| `400` | ошибка в запросе |
| `401`, `403` | нужна авторизация / доступ запрещён |
| `404` | не найдено |
| `500` | ошибка на сервере |

Запрос к API обычно возвращает JSON. Его удобно читать через `jq`:

```bash
curl -s http://localhost:8000/health | jq
```

```text
{
  "status": "ok",
  "database": "ok",
  "version": "0.2.0"
}
```

Это адрес проверки состояния учебной платформы — попробуй, когда она запущена.

Отправка данных методом POST:

```bash
curl -X POST http://localhost:8000/api/items \
  -H "Content-Type: application/json" \
  -d '{"name": "sw-1", "ports": 24}'
```

`-X` задаёт метод, `-H` добавляет заголовок, `-d` передаёт тело запроса.
Обратная косая черта в конце строки переносит команду на следующую строку.
Именно в таком виде в документации приводят примеры запросов к нейросетям.

## Скачивание файлов

```bash
wget https://example.com/file.zip          # скачать файл
curl -LO https://example.com/file.zip      # то же через curl
```

## Порядок диагностики «сервис не открывается»

1. Процесс запущен? → `ps aux | grep имя` или `systemctl status`.
2. Порт слушается? → `ss -tulpn | grep :порт`.
3. На каком адресе? → `127.0.0.1` или `0.0.0.0`.
4. Локально отвечает? → `curl -v http://localhost:порт`.
5. Узел доступен по сети? → `ping`, затем `nc -zv адрес порт`.
6. Не мешает ли межсетевой экран? → `sudo ufw status`.

Двигайся снизу вверх по уровням — так же, как при поиске неисправности в сети.
